# CPBooke — توثيق النظام الكامل

نظرة شاملة لمنصة **CPBooke (لوحة تحكم Booke)**: ماذا تقدم، كيف تعمل، الوحدات، نقاط القوة والضعف، الإيجابيات والسلبيات، وما الذي يجب الانتباه له تشغيلياً.

> ملاحظة: تفاصيل محافظ المزوّدين موثّقة بعمق في  
> [`docs/provider-wallets-system.md`](./provider-wallets-system.md)

---

## 1) ما هي المنصة؟

**CPBooke** هي **لوحة تحكم تشغيلية ومالية** لوكالة سفر/منصة Booke، وليست محرك بحث حجوزات (GDS) بحد ذاتها.

### الفكرة باختصار
1. الزبون يحجز عبر التطبيق / مزوّد خارجي (مثل BookNow).
2. الحجز يُزامَن إلى CPBooke.
3. فريق الوكالة يدير الطلب، الدعم، المالية، الولاء، والإشعارات من مكان واحد.
4. يتم تتبع رصيد الوكالة المسبق عند المزوّدين (Provider Wallets).

### سطحان رئيسيان
| السطح | لمن؟ | التقنية |
|--------|------|---------|
| `/admin/*` | فريق الوكالة (تشغيل، دعم، مالية…) | Laravel + Inertia + Vue 3 |
| `/api/v1/*` | تطبيق الموبايل / العملاء | Laravel API + Sanctum |

## 2) ماذا يقدم النظام من طرف لطرف؟

1. **حسابات عملاء** عبر API: تسجيل، دخول، ملف شخصي، مسافرين محفوظين، مفضلات.
2. **مزامنة الحجوزات** بعد الشراء (`sync-flight`) مع رقم طلب داخلي وحالة دفع/تشغيل.
3. **تشغيل الطلبات** من الأدمن: حالات، ملاحظات، سجل تغييرات، تفاصيل مالية.
4. **مالية الزبون**: مدفوعات، استرجاعات، تعويضات، دفتر قيد مزدوج، تقارير ومطابقة.
5. **محافظ المزوّدين**: إيداع يدوي + خصم تلقائي عند الحجز المدفوع.
6. **الدعم**: تذاكر، محادثة لحظية، SLA، إلغاء/استرجاع/تعويض من التذكرة.
7. **الولاء**: مستويات، قواعد، مزايا، وربط بمعاينة التسعير.
8. **الإشعارات**: قوالب وتسليم عبر قنوات متعددة.
9. **المطارات**: دليل + استيراد BookNow + مطارات مميزة للتطبيق.
10. **الحوكمة**: لوحة مركزية لصحة الصلاحيات والمالية والإشعارات والولاء.

---

## 3) المكدس التقني

- **Backend:** PHP / Laravel
- **Admin UI:** Vue 3 + Inertia.js + Tailwind + Vite
- **API Auth:** Laravel Sanctum
- **Admin Auth:** جلسات ويب (Breeze) + صلاحيات RBAC
- **Database:** MySQL (افتراضي)
- **Queue / Cache / Session:** غالباً Database (Redis اختياري)
- **Realtime:** Laravel Reverb (محادثة الدعم)
- **اختبارات:** PHPUnit (+ Vitest لبعض الواجهة)
- **لغة الأدمن:** إنجليزي / عربي

## 5) كيف تسير الحجز والمال؟

### تدفق الحجز الأساسي (BookNow)

```
التطبيق يحجز عند المزوّد
        ↓
POST /api/v1/orders/sync-flight
        ↓
حفظ/تحديث الطلب (Idempotent حسب booking_id)
        ↓
إن كان مدفوعاً:
  • تسجيل Payment في المالية
  • خصم من محفظة المزوّد (BookNow)
        ↓
أحداث → إشعارات + إعادة حساب الولاء
```

**مهم:** CPBooke حالياً نظام **ما بعد الحجز** (System of Record تشغيلي)، وليس محرك بحث تذاكر حي داخل هذا المستودع.

### طبقات المال (لا تخلط بينها)

| الطبقة | المعنى |
|--------|--------|
| **Financial Transactions + Ledger** | مال الزبون/الطلب: دفع، استرجاع، تعويض، قيد مزدوج |
| **Provider Wallets** | رصيد الوكالة المسبق عند شركة المزوّد |
| **Wallet في صفحة العميل (أدمن)** | رقم **محسوب** من معاملات الطلبات، وليس محفظة مخزنة حقيقية |

## 6) الدعم والولاء والإشعارات

### الدعم
- تذاكر مربوطة بمستخدم/طلب
- أولوية + نوافذ SLA
- محادثة لحظية
- إجراءات على الطلب من التذكرة: إلغاء، استرجاع كلي/جزئي، تعويض، عكس استرجاع
- تقارير حل وتصدير

### الولاء
- مستويات وقواعد ومزايا
- يُحدَّث مع الطلبات والمدفوعات والاسترجاعات
- يدخل في محرك التسعير (`/pricing/preview`)

### الإشعارات
قنوات مدعومة مفاهيمياً: In-App، Email، Push، SMS، WhatsApp  
تُطلق عند أحداث مثل: إنشاء/تأكيد طلب، دفع، استرجاع، رد دعم، تغيير مستوى ولاء، أعطال مالية حرجة.

## 7) نقاط القوة (للنظام ككل)

1. **منصة تشغيل متكاملة** بعد الحجز: طلبات + دعم + مالية + ولاء.
2. **بنية وحدات واضحة** (`Admin` / `Api` / Domains).
3. **RBAC قوي** مناسب لتوزيع العمل بين تشغيل/دعم/مالية.
4. **فصل طبقات المال** (زبون vs مزوّد) يقلل الخلط المحاسبي.
5. **Idempotency** في مزامنة الحجوزات وخصم المحفظة.
6. **أثر تدقيقي** (سجل طلبات، دفتر مالي، أحداث دعم، حوكمة).
7. **API جاهز للتطبيق** (مسافرين، مفضلات، دعم، إشعارات).
8. **واجهة أدمن ثنائية اللغة** (EN/AR).
9. **قابلية توسع للمزوّدين** عبر Provider Wallets + خدمة خصم عامة.
10. **اختبارات تغطي** أجزاء حساسة (طلبات، صلاحيات، محافظ، دعم…).

---

## 8) نقاط الضعف / الفجوات / المخاطر

1. **لا يوجد بحث/حجز GDS حي داخل CPBooke** — الاعتماد على التطبيق/BookNow.
2. مسار إنشاء الطلب القديم يعتمد جزئياً على **Mock Provider**.
3. خصم محفظة المزوّد حالياً غالباً على **سعر البيع (`grand_total`)** وليس بالضرورة تكلفة المزوّد الصافية.
4. **إيداع محفظة المزوّد يدوي** — قد يحدث فرق مع رصيد بوابة الشركة.
5. استرجاع الزبون **لا يعيد تلقائياً** رصيد محفظة المزوّد.
6. سياسة السالب بدون **سقف ائتمان رقمي** محدد.
7. «محفظة العميل» في الأدمن **عرض مشتق** وقد تُفهم خطأ كرصيد نقدي مخزّن.
8. تكامل بوابات الدفع ليس موديول مستقل ناضج (الحالة غالباً من الـ sync/الأدمن).
9. عمق قنوات SMS/WhatsApp/Push قد يحتاج تجهيز إنتاجي إضافي.
10. وحدة Settings ما زالت أخف من باقي الوحدات.
11. التشغيل الإنتاجي يحتاج **Queue workers** و(للشات) إعداد Realtime.
12. README الأساسي أبسط من حجم النظام الفعلي.

## 9) الإيجابيات للوكالة

- مكان واحد لإدارة ما بعد البيع وخدمة الزبون.
- توزيع أدوار واضح بدون مشاركة حساب سوبر أدمن مع الجميع.
- تتبع رصيد المزوّد المسبق — ضروري لنموذج الإيداع عند الشركة.
- قابلية التدقيق والمطابقة المالية.
- ولاء وإشعارات لدعم الاحتفاظ بالعملاء دون إعادة بناء محرك الحجز.
- جاهزية للموبايل عبر API.
- مناسب لفريق إقليمي يعمل بالعربية والإنجليزية.

## 10) السلبيات / تحفظات تشغيلية

- يجب التعامل مع CPBooke كـ **سجل تشغيلي ومالي**، لا كبديل كامل لمحرك البحث عند المزوّد.
- الإيداع اليدوي لمحفظة المزوّد يحتاج انضباط يومي وإلا يظهر فرق مع الواقع.
- الاسترجاع للزبون ≠ استعادة رصيد عند المزوّد تلقائياً (حالياً).
- تقارير التكلفة قد تضلل إن اعتبرتم خصم المحفظة = تكلفة المزوّد الحقيقية دون ضبط الحقل.
- يحتاج تشغيل Queue (+ Realtime للشات) في الإنتاج.
- تدريب الفريق ضروري لعدم خلط مفاهيم «محفظة الزبون» و«محفظة المزوّد» و«دفتر المالية».
- التوسع لفندق/eSIM/تأمين يحتاج قواعد خصم وحقول تكلفة أوضح لكل منتج.

## 11) لمن يناسب النظام؟

**يناسب إذا كنتم:**
- وكالة/منصة تعتمد مزوّداً خارجياً للحجز.
- تحتاجون تشغيل طلبات + دعم + مالية مركزية.
- تودعون رصيداً مسبقاً عند المزوّد وتريدون تتبعه.
- لديكم تطبيق عملاء وAPI.

**أقل ملاءمة إذا كنتم تريدون فقط:**
- محرك بحث تذاكر مستقل داخل نفس المشروع دون تكامل خارجي.
- محفظة إلكترونية كاملة للزبائن (Stored Value) كمنتج مالي مستقل.
- مزامنة لحظية مضمونة مع رصيد بوابة المزوّد بدون إدخال يدوي.

## 13) الخلاصة التنفيذية

**CPBooke** منصة تشغيل ووكالة متقدمة لما بعد الحجز: تجمع الطلبات، الدعم، المالية، الولاء، الإشعارات، ومحافظ المزوّدين في لوحة واحدة مع API للموبايل.

- **أقوى ما فيها:** التكامل التشغيلي، الصلاحيات، فصل المال، التدقيق، وقابلية التوسع.
- **أضعف ما فيها اليوم:** الاعتماد على مصدر الحجز الخارجي، دقة تكلفة المزوّد، والمزامنة اليدوية لرصيد الشركة، وعدم اكتمال بعض مسارات الاسترجاع/التنبيه حول محافظ المزوّدين.

هي **أساس قوي لتشغيل وكالة رقمية**، بشرط فهم حدودها: نظام سجل وتحكم، وليس محرك حجز حي كامل بمفرده.
