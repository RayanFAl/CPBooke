# نظام محافظ المزوّدين (Provider Wallets)

> هذا الملف يشرح **جزء محافظ المزوّدين فقط**.  
> للنظام الكامل (طلبات، مالية، دعم، ولاء، API…):  
> [`docs/cpbooke-system-overview.md`](./cpbooke-system-overview.md)

توثيق عملي للنظام كما هو منفّذ في CPBooke حالياً: ماذا يقدم، كيف يعمل، نقاط القوة والضعف، الإيجابيات والسلبيات، والحدود المعروفة.

---

## 1) ما المشكلة التي يحلّها؟

أنتم وكالة تودعون رصيداً مسبقاً عند شركات مزوّدين (مثل BookNow)، ثم يخصم المزوّد من رصيدكم عند كل خدمة (حجز رحلة، لاحقاً فندق / eSIM / تأمين…).

بدون هذا النظام:
- لا يوجد مكان واحد يوضح: كم أودعتم؟ كم خُصم؟ كم تبقّى؟
- صعوبة تتبع الحركة المالية لكل مزوّد على حدة.
- اختلاط رصيد المزوّد مع مالية الطلبات الخاصة بالزبائن.

**الهدف:** دفتر رصيد وكالة عند كل مزوّد، منفصل عن محفظة الزبون وعن دفتر المدفوعات/الاسترجاعات.

---

## 2) ماذا يقدم النظام؟

| القدرة | التفاصيل |
|--------|----------|
| مزودون مستقلون | جدول `providers` (اسم، مفتاح، حالة) |
| محفظة لكل مزود | مرتبطة بـ `provider_id` وليس بالنص فقط |
| عملات متعددة | نفس المزوّد يمكنه امتلاك محفظة LYD وأخرى USD |
| بيئات متعددة | `production` و `sandbox` لنفس المزوّد/العملة |
| إيداع يدوي | سوبر أدمن يسجّل الشحن بعد التحويل للمزوّد |
| خصم عام | `WalletService::debit(...)` لأي تكامل |
| سجل حركات | نوع الحركة + مرجع + وصف + رصيد بعد العملية |
| سياسة رصيد صريحة | السماح بالسالب أو رفض العملية عند عدم الكفاية |
| واجهة أدمن | قائمة محافظ، إنشاء مزود/محفظة، إيداع، تعديل، كشف حركة |
| صلاحيات | مشاهدة لمن لهم `provider-wallets.view`، إدارة لـ `provider-wallets.manage` (سوبر أدمن) |

### الربط الحالي مع الحجوزات
عند `sync-flight` لطلب **مدفوع**:
1. يُجلب/يُنشأ مزود `booknow`.
2. يُستدعى الخصم عبر الخدمة العامة.
3. المرجع يكون من نوع `flight_booking` مع `order_id`.
4. العملية **idempotent** (إعادة نفس الـ sync لا تخصم مرتين).

---

## 3) كيف يعمل؟ (تدفق مبسّط)

```
[سوبر أدمن]
   │
   ├─ إنشاء Provider (BookNow / Duffel / …)
   ├─ إنشاء Wallet (عملة + بيئة + سياسة الرصيد)
   └─ Deposit يدوي  ──► يزيد الرصيد

[تكامل API: Flights / Hotels / …]
   │
   └─ WalletService::debit(providerId, amount, currency, referenceType, referenceId)
         │
         ├─ يجد المحفظة المناسبة (مزود + عملة + بيئة)
         ├─ يتحقق من السياسة (سالب مسموح؟)
         ├─ يخصم ويحفظ الحركة
         └─ يربط المرجع (مثلاً flight_booking #1542)
```

### الجداول الأساسية

**`providers`**
- `id`, `name`, `key`, `status`

**`provider_wallets`**
- `provider_id`, `currency`, `environment`, `balance`
- `low_balance_threshold`, `allow_negative`, `is_active`

**`provider_wallet_transactions`**
- `type`: deposit / debit / adjustment / refund (جاهز للاستخدام)
- `amount`, `balance_after`, `currency`
- `reference_type`, `reference_id`, `description`
- `order_id` (اختياري لتسهيل الربط مع الطلبات)
- `created_by`, `metadata`

Unique مهم: محفظة واحدة فقط لكل `(provider_id, currency, environment)`.

## 4) نقاط القوة

1. **فصل واضح للمسؤولية**  
   رصيد المزوّد ≠ مدفوعات الزبون ≠ دفتر المالية العام للطلبات.

2. **تصميم متعدد المزوّدين**  
   جاهز لـ BookNow وDuffel وAiralo وغيرها دون خلط الأرصدة.

3. **خدمة خصم مركزية**  
   أي تكامل جديد يستدعي `WalletService` بدل تكرار منطق الخصم.

4. **مراجع قابلة للتتبع**  
   كل حركة تعرف من أين جاءت (`flight_booking`, `manual`, …).

5. **Idempotency**  
   يمنع الخصم المزدوج عند إعادة إرسال نفس العملية.

6. **سياسة رصيد معلنة**  
   ليست سلوكاً غامضاً: إما Overdraft أو Reject، على مستوى المحفظة + إعداد افتراضي في `.env`.

7. **دعم بيئة وتجربة**  
   فصل sandbox عن production يقلل خطر تلويث رصيد الإنتاج.

8. **صلاحيات مناسبة للمرحلة**  
   الإيداع/الإنشاء محصور في الإدارة العليا؛ المالية يمكنها المشاهدة.

---

## 5) نقاط الضعف / الحدود الحالية

1. **الإيداع يدوي فقط**  
   لا يوجد مزامنة تلقائية مع رصيد المزوّد الحقيقي عبر API الشركة.

2. **مبلغ الخصم من الحجز = `grand_total`**  
   قد لا يساوي تكلفة الوكالة عند المزوّد إذا كان هناك عمولة/هامش. لا يُستخدم حالياً `base_amount` أو `commission_amount` كأساس للخصم من محفظة المزوّد.

3. **لا يوجد Credit Limit رقمي منفصل**  
   السياسة ثنائية: سماح بالسالب أو رفض. لا يوجد سقف ائتمان مثل «مسموح حتى -2000 فقط».

4. **لا يوجد تنبيه آلي**  
   تنبيه الرصيد المنخفض/السالب يظهر في الواجهة، بدون إيميل/إشعار فوري بعد.

5. **لا يوجد Refund تلقائي للمحفظة**  
   عند استرجاع حجز للزبون، رصيد المزوّد لا يُعاد تلقائياً (نوع `refund` موجود في النموذج لكن التدفق غير مربوط بعد).

6. **لا توجد تقارير متقدمة**  
   كشف حركة أساسي موجود؛ لا يوجد بعد تقرير شهري/مقارنة مع فاتورة المزوّد/تصدير محاسبي مخصص للمحافظ.

7. **إنشاء المحفظة التلقائي عند أول خصم**  
   مفيد للتشغيل، لكنه قد ينشئ محفظة برصيد 0 ثم يدخل السالب إذا نُسي الإيداع مسبقاً (مع سياسة السماح بالسالب).

8. **الواجهة إدارية فقط**  
   لا يوجد API للموبايل لعرض رصيد المزوّد (وهذا متعمد غالباً لأنه شأن تشغيلي داخلي).

---

## 6) الإيجابيات (لماذا يستحق النظام؟)

- وضوح مالي: تعرفون وضع كل مزوّد بسرعة.
- جاهزية للتوسع لأكثر من API دون إعادة تصميم الجذور.
- تقليل الأخطاء البشرية في «حساب الرصيد على إكسل».
- أثر تدقيقي: من أودع؟ متى؟ لأي حجز خُصم؟
- فصل sandbox/production يحمي التشغيل الحقيقي.
- يتماشى مع نموذج أعمال الوكالة (prepaid عند المزوّد).

---

## 7) السلبيات (ما يجب الانتباه له)

- الاعتماد على الإدخال اليدوي للإيداع يعني أن أي نسيان = فرق بين النظام والواقع.
- إذا كان سعر الزبون ≠ تكلفة المزوّد، التقارير قد تضلل إن اعتبرتم الخصم «تكلفة حقيقية» دون ضبط الحقل.
- السماح بالسالب بدون سقف قد يراكم مديونية غير مرئية إن لم تُراقب يومياً.
- حتى يُربط الاسترجاع، قد يظهر رصيد المزوّد أقل من الواقع بعد Refund من طرف الشركة.
- النظام يتتبع **ما تسجلونه عندكم**، وليس بالضرورة الرصيد الرسمي داخل بوابة المزوّد إلا إذا أضفتم مزامنة لاحقاً.

---

## 8) الصلاحيات والإعدادات

### Permissions
- `provider-wallets.view` — مشاهدة الأرصدة والحركات
- `provider-wallets.manage` — إنشاء مزود/محفظة + إيداع + تعديل

افتراضياً: الإدارة العليا تملك الإدارة؛ المالية/الأدمن يمكنهم المشاهدة حسب توزيع الأدوار.

### Environment
```env
WALLET_ALLOW_NEGATIVE=true
WALLET_DEFAULT_ENVIRONMENT=production
```

## 9) مسار الاستخدام اليومي المقترح

1. تأكدوا من وجود المزوّد (مثلاً BookNow).
2. أنشئوا محفظة العملة/البيئة الصحيحة.
3. بعد كل تحويل للمزوّد: سجّلوا **Deposit**.
4. دعوا التكاملات تخصم تلقائياً عبر `WalletService`.
5. راقبوا الرصيد والحركات؛ إذا اقترب من الحد أو سالب: اشحنوا.
6. عند فرق مع كشف المزوّد: استخدموا **Adjustment** مع ملاحظة واضحة.

---

## 10) توصيات تطوير لاحقة (اختياري)

| الأولوية | التحسين |
|----------|---------|
| عالية | خصم حسب تكلفة المزوّد (cost) بدل/إلى جانب `grand_total` |
| عالية | إعادة رصيد المزوّد عند Refund/Cancel المعتمد |
| متوسطة | سقف ائتمان رقمي (`credit_limit`) بدل سماح مطلق بالسالب |
| متوسطة | تنبيهات عند انخفاض الرصيد |
| متوسطة | تصدير CSV/Excel لكشف المحفظة |
| منخفضة | مزامنة رصيد المزوّد من API الشركة (إن وُجد) |
| منخفضة | مطابقة شهرية (Reconciliation) بين حركتنا وفاتورة المزوّد |

---

## 11) الخلاصة

النظام الحالي هو **دفتر رصيد تشغيلي متعدد المزوّدين** مناسب لمرحلة الوكالة التي تودع يدوياً وتتابع الخصم من الحجوزات المتزامنة.

- **قوي في:** الفصل، التوسع، التتبع، الخدمة المركزية، السياسة الصريحة.
- **ضعيف في:** المزامنة مع رصيد الشركة الحقيقي، دقة تكلفة المزوّد، الاسترجاع التلقائي، التنبيهات المتقدمة.

هو أساس صحيح للبناء عليه، وليس بديلاً كاملاً بعد عن محاسبة المزوّد الرسمية أو تكامل الرصيد اللحظي مع بوابة الشركة.
